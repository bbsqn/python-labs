Лабораторна робота №2 з дисципліни «Професійний Python».  
**Тема:** Структури даних та функціональна декомпозиція.  
**Індивідуальний варіант 4:** «Аналіз системи банківських рахунків».

## Description

Модуль обробки та аналізу структурованих даних банківської системи. Реалізовано професійне використання вбудованих та розширених структур даних Python (`list`, `tuple`, `set`, `dict`, `collections.Counter`, `collections.defaultdict`, `collections.deque`), функціональну декомпозицію, розширені параметри функцій (`*args`, `**kwargs`), анонімні функції (`lambda`), замикання (`closure`) та декоратори (`decorators`).

### Реалізований функціонал (Варіант 4):
1. **Пошук рахунку за номером:** лінійний пошук $O(n)$ та швидкий пошук через індекс $O(1)$.
2. **Групування рахунків за типом:** реалізовано за допомогою `collections.defaultdict(list)`.
3. **Загальна сума коштів:** агрегація через `sum()`.
4. **Середній баланс:** обчислення із застосуванням генераторного виразу та декоратора `@measure_time`.
5. **Рахунок із найбільшим та найменшим балансом:** пошук за допомогою `max()` / `min()` з `lambda`.
6. **Фільтрація рахунків за мінімальним балансом:** за допомогою `list comprehension` та фабрики замикань `create_balance_filter(min_balance)`.
7. **Сортування за балансом:** за допомогою `sorted()` з `lambda` за спаданням та зростанням.
8. **Dict-index за номером рахунку:** швидкий хеш-індекс через `dict comprehension`.

### Завдання підвищеної складності (Section 38):
- Універсальна функція фільтрації вищого порядку `filter_items(items, predicate)`.
- Універсальне сортування `sort_accounts(accounts, key_func, reverse)`.
- Параметризований декоратор `@repeat(count)`.
- Фабрики замикань `create_balance_filter` та `create_type_filter`.
- Вкладене групування `group_by_nested`.
- Підрахунок розподілу рахунків через `collections.Counter`.
- Історія останніх операцій за допомогою `collections.deque(maxlen=N)`.
- Ланцюгова обробка даних через `pipeline(data, *operations)`.
- Експорт зведеної статистики `export_summary(accounts)`.
- Експериментальне вимірювання швидкодії (benchmark) для 1 000, 10 000 та 100 000 записів.

## Оцінка складності операцій (Big-O)

| Операція | Структура даних | Складність (середня) | Пояснення |
| :--- | :--- | :--- | :--- |
| Пошук за номером | `list` | $O(n)$ | Послідовний перебір елементів списку |
| Пошук за номером | `dict` (index) | $O(1)$ | Хеш-таблиця забезпечує миттєвий доступ за ключем |
| Перевірка наявності типу | `set` | $O(1)$ | Хешування елементів множини |
| Групування за типом | `defaultdict` | $O(n)$ | Одноразовий прохід по списку з додаванням у хеш-карту |
| Сортування за балансом | `list` (Timsort) | $O(n \log n)$ | Алгоритм Timsort, вбудований у Python |

## Результати Benchmark (Секція 37)

| Кількість записів | Пошук у `list` (лінійний) | Пошук у `dict` (хеш-індекс) | Прискорення |
| :--- | :--- | :--- | :--- |
| **1 000** | 0.00007850 s | 0.00000130 s | ~60x швидше |
| **10 000** | 0.00092490 s | 0.00000170 s | ~544x швидше |
| **100 000** | 0.00779210 s | 0.00000400 s | ~1948x швидше |

**Висновок:** Експеримент на практиці доводить, що час лінійного пошуку в `list` зростає прямо пропорційно до кількості елементів ($O(n)$), тоді як пошук за ключем у `dict` зберігає константний час ($O(1)$), демонструючи критичну важливість вибору відповідних структур даних для високопродуктивних систем.
