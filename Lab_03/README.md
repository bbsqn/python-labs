## 1. Опис проєкту

Проєкт реалізує повноцінний лінивий (lazy) потоковий конвеєр обробки великих наборів даних банківських операцій без необхідності завантаження всього набору даних в оперативну пам'ять (memory-efficient streaming pipeline).

### Вхідні дані
CSV-файл із структурою колонок:
```csv
account_number,client,balance,operation,amount
```
- `account_number`: унікальний ідентифікатор рахунку (наприклад, `UA0000001`).
- `client`: ім'я клієнта (наприклад, `Ivan Petrenko`).
- `balance`: початковий баланс рахунку.
- `operation`: тип операції (`deposit`, `withdraw`, `check`).
- `amount`: сума транзакції.

### Особливості бізнес-логіки варіанта 4
- **Потокова валідація:** фільтрація порожніх значень, перевірка коректності типів, відсікання від'ємних балансів/сум та невідомих операцій.
- **Потокове застосування операцій:**
  - `deposit`: збільшення балансу на `amount`.
  - `withdraw`: зменшення балансу на `amount` із жорстким контролем **недопущення від'ємного балансу** (операція відхиляється, якщо баланс недостатній).
  - `check`: перевірка рахунку (баланс залишається незмінним).
- **Потокова фільтрація:** відсікання рахунків за мінімальним порогом балансу або пошук за клієнтом.
- **Потокова аналітика:** розрахунок агрегованої статистики (загальні кошти, середній баланс, мінімум/максимум, розподіл за типами операцій) за один прохід конвеєра.

## 2. Схема потокового конвеєра

```text
       [ Вхідний CSV файл ]
                │
                ▼
      read_lines() (yield from)
                │
                ▼
          clean_lines()
                │
                ▼
     parse_csv_rows() (yield from)
                │
                ▼
       validate_accounts()
                │
                ▼
       apply_operations()
  (захист від від'ємного балансу)
                │
                ▼
       normalize_clients()
                │
                ▼
       filter_by_balance()
                │
                ▼
  [ Споживач (Sink) ]:
  ├─ calculate_statistics()
  ├─ batched_records()
  ├─ streaming_total_funds()
  └─ find_first_account() (early termination)
```

## 4. Вимоги та реалізовані можливості

| Вимога методички | Реалізація в коді | Опис |
|---|---|---|
| Власний iterator class | `AccountRangeIterator`, `AccountRange` | Реалізація протоколу `__iter__` та `__next__` з підтримкою незалежних повторних обходів |
| Генераторні функції з `yield` | `clean_lines`, `apply_operations`, `batched_records` та ін. | Ліниве генерування результатів у міру потреби |
| Делегування через `yield from` | `read_lines`, `parse_csv_rows`, `recursive_flatten` | Прозора передача ітерації без ручних вкладених циклів |
| Generator expressions | `streaming_total_funds`, `cumulative_balances` | Обчислення сум без проміжних списків: `sum(a.balance for a in records)` |
| `itertools.islice` | `batched_records`, зрізи потоку в `main.py` | Отримання частини нескінченного або великого потоку |
| `itertools.chain` | `read_files_chain` | Потокове об'єднання декількох джерел даних без склеювання списків |
| `itertools.accumulate` | `cumulative_balances` | Кумулятивний розрахунок динаміки коштів |
| `itertools.pairwise` | `pairwise_amount_differences` | Аналіз різниць сум між послідовними транзакціями |
| `itertools.groupby` | `group_by_operation` | Групування записів за типом транзакцій |
| `itertools.count` | `infinite_account_stream` | Створення нескінченного генератора рахунків |
| Batch processing | `batched_records`, `dynamic_batched` | Пакетування записів за фіксованим розміром або сумою операцій |
| Early termination | `find_first_account` | Миттєве припинення обробки при знаходженні першого співпадіння |

## 5. Результати експериментального порівняння (Eager vs Lazy)

Вимірювання проведено на реальних згенерованих датасетах за допомогою модулів `time.perf_counter()` та `tracemalloc`.

| Кількість записів | Eager Time (s) | Lazy Time (s) | Eager Peak RAM (MB) | Lazy Peak RAM (MB) | Time to First Result (s) |
|---|---|---|---|---|---|
| **10 000** | 0.0705 | 0.0635 | 4.64 | 0.19 | 0.000270 |
| **100 000** | 0.7704 | 0.6860 | 45.00 | 0.19 | 0.000268 |
| **500 000** | 3.8734 | 3.4654 | 224.54 | 0.19 | 0.000301 |

### Експеримент з Early Termination (100 000 записів)
- **Eager час пошуку першого елемента:** 0.209648 с (необхідність спочатку завантажити та зберегти всі 100 000 записів).
- **Lazy час пошуку першого елемента:** 0.000372 с (зупинка ітератора одразу після знаходження першого результату).
- **Прискорення (Speedup):** **563.6x**.

### Висновки з експерименту
1. **Використання пам'яті:** Lazy-підхід демонструє константну складність за пам'яттю $O(1)$ (~0.19 МБ) незалежно від обсягу даних, тоді як Eager зростає лінійно $O(N)$ (досягаючи понад 224 МБ для 500 тис. записів).
2. **Швидкість початку відгуку (TTFR):** Генератори надають перший елемент практично миттєво (~0.27 мс).
3. **Раннє переривання:** При пошуку конкретного запису або перших $N$ елементів лінивий конвеєр у сотні разів випереджає жадібний метод.
